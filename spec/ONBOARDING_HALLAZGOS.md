# Registro de hallazgos — Fase 2 (Onboarding técnico)

> Versión: 1.0 | Fecha: 2026-09-21 | Se actualiza durante cada bloque de `PLAN_ONBOARDING.md`.
> **Regla de la fase: aquí se ANOTA, no se arregla.** Cada fila es una decisión para el líder; ninguna se implementa sin abrir antes un gate de desarrollo (y un ADR si toca una decisión cerrada).

## Cómo se lee

**Severidad**: **Alta** = puede causar pérdida/exposición de datos o sobreventa en uso normal · **Media** = riesgo real pero con condiciones (concurrencia, atacante, fallo de infraestructura) o mala documentación que engaña · **Baja** = deuda o detalle sin consecuencia inmediata.
**Tipo**: Seguridad · Concurrencia · Bug · Deuda · Doc · UX · Operación · Proceso · Decisión de negocio.
**Origen**: **Documentado** = ya está escrito en `spec/` (se cita dónde) · **Detectado** = encontrado leyendo el código al preparar la fase (se cita archivo:línea).
**Estado**: **Verificado** = confirmado leyendo el código en 2026-09-21 · **Por verificar (Kx)** = la fuente es un documento; **la documentación de este repo demostró desfasarse del código (H-014, H-025), así que estas filas NO se enseñan como hecho hasta contrastarlas con el código en su gate** · **Abierto** · **Descartado**.
**Regresión** (en la columna Origen) = el problema ya había sido corregido en algún momento y el arreglo no sobrevivió; el remedio es conocido.
**Decisión sugerida**: propuesta de **qué haría falta**, no un cambio hecho.

## Observaciones (opinión sin consecuencia verificable; no cuentan como hallazgos)

- `apps/api/src/registration/service.ts` concentra confirmar, editar, cancelar y consultar en 584 líneas: es el archivo más grande y el más crítico; un entrevistador preguntará por qué no está partido.
